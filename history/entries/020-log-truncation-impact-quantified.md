# 020 · MAX_CONTENT_CHARS 截断对 log 特征的实测损耗 + 阈值-耗时曲线

- **日期**: 2026-07-28
- **PR**: 待定（讨论产生于 PR #20 review 之后，尚未开新分支）
- **类型**: Docs（实测记录，未改代码）
- **影响域**: `src/preprocessors/log_preprocessor.py`（MAX_CONTENT_CHARS 相关注释与行为描述）

## 做了什么

PR #20 的 review 中，多个审查角度独立指出 entry 019 里"截断只影响喂给 Drain3 的内容，不改变 template_id 的行首语义"（`log_preprocessor.py:40-42` 注释）与"行为不变"（entry 019 第 12 条）的表述不准确。本次用真实数据（`data/normal_v2`、`data/new_ep1`）实测了截断对 3 个 log 特征的具体影响幅度，以及截断阈值与 Drain3 处理耗时的关系曲线，供后续决策参考。本次只做实测记录，未修改任何代码。

## 关键决策（不在 commit 里）

- **先量化再决定是否改阈值**：用户提出"增大阈值能否减少信息损耗"的问题，没有直接调参，而是先跑基准测试搞清楚"阈值-耗时"和"阈值-信息损耗"两条曲线的形状，避免凭直觉判断。
- **本次不修改 `MAX_CONTENT_CHARS` 的值**：实测显示把阈值从 2000 提到 3000 对 CPU 几乎零代价，但对信息损耗的改善也很有限（见下）——不是一个"明显划算"的改动，留给用户决定是否要做，或者转向做一个独立的"超长行占比"特征来对症解决。

## 坑 / 已知问题

- **entry 019"行为不变"的表述不准确，只对短行成立**：用 `data/normal_v2/normal_0711_60` 的 order-service + seat-service 日志（38279 行）实测，截断（2000 字符）vs 不截断两次独立跑 Drain3：
  - 短行（≤2000 字符，占比 88.4%，33823 行）：template_id 与不截断时 **100% 一致**，0 差异。
  - 超长行（>2000 字符，占比 11.6%，4456 行）：template_id 与不截断时 **100% 不同**（4450/4456 或用 template 字符串比对为 4456/4456，取决于比较口径）。
  - 落到最终特征：`service_log__event_rate`、`service_log__error_ratio` 完全不受截断影响（只看行数/日志级别，不看内容）；`service_log__template_diversity` 受影响，363 个 15s 窗口里 219 个（60%）取值发生变化，平均绝对偏差 0.0167，最大偏差 0.16（该特征取值范围 [0,1]，均值约 0.24）。
  - 结论：注释里"不改变 template_id 的行首语义"这句话对 88.4% 的行是对的，但对超长行本身是错的——只是超长行占比不到 12%，所以整体特征损耗是"中等"而非"灾难性"。

- **阈值-耗时曲线不是缓慢线性增长，而是存在陡峭跳变**：用 new_ep1 里含 97 万字符单行（`Lv_E_HTTPREPLACE_order` case 的 seat-service 日志，单文件 46941 行）实测：

  | 截断阈值（字符） | 处理耗时 | 相对 2000 阈值倍数 |
  |---|---|---|
  | 2000（当前生产值） | 0.30s | 1x |
  | 3000 | 0.31s | 1.05x |
  | 5000 | 0.36-0.38s | ~1.2x |
  | 10000 | 0.49-0.51s | ~1.6x |
  | 20000 | 0.69-0.75s | ~2.3x |
  | 50000 | 1.35s | ~4.5x |
  | 100000 | 2.46s | ~8x |
  | 不截断（97万字符） | 23.6-27.6s | **~80x** |

  从当前值 2000 涨到 20000 耗时才 2.3 倍，但从 20000 涨到"不截断"直接跳到 80 倍——真正的 CPU 爆炸只发生在阈值远超当前值、逼近数据集里的真实离群值（几十万字符）时。当前 2000 这个默认值本身留了很大的安全边际。

- **提高阈值对信息损耗的改善远小于预期，且很快见顶**：同一份 new_ep1 数据上，阈值-template_diversity 偏差曲线：

  | 截断阈值 | 平均绝对偏差 | 最大绝对偏差 | 受影响窗口 |
  |---|---|---|---|
  | 2000 | 0.0191 | 0.1364 | 142/142 |
  | 3000 | 0.0164 | 0.1364 | 142/142 |
  | 5000 | 0.0158 | 0.0909 | 142/142 |
  | 10000 | 0.0158 | 0.0909 | 142/142 |
  | 20000 | 0.0187 | 0.1364 | 142/142 |

  2000→3000 平均偏差只改善 14%，且 142 个窗口全部仍受影响（"受影响窗口数"没有减少，只是每个窗口的偏差幅度略降）。继续加大阈值到 5000/10000 有小幅改善后迅速见顶，20000 反而比 5000/10000 略差（Drain3 聚类算法本身对输入长度的响应不是单调的）。根因是这个数据集里存在极端离群值（几十万到近百万字符的"整个业务对象列表打印"），任何"几千字符量级"的阈值相对这些离群值本质上都是截断，差别不大——真正显著改善需要把阈值提到几万到十几万字符量级，但那时 CPU 耗时已经涨到 4-8 倍（单文件层面；new_ep1 单文件可达 4.8GB，实际生产环境的耗时倍数会更极端）。
